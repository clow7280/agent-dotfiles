# Markdown 文档规范

本规范仅适用于项目内的文档写作，领域报告、学术论文等成品文书默认不适用，除非用户明确要求。

## 基本格式

- 永远使用 CommonMark 标准语法编写文档，除非用户明确指定其他方言
  - CommonMark 是对 Markdown 语法的标准化规范，消除了各实现之间的歧义
  - 在此基线上仅允许使用表格这一项 GFM 扩展语法
- 标点按所在上下文的语言选择，中文上下文使用全角标点，英文上下文使用 ASCII 标点
  - 引号同样按此规则处理，中文上下文使用“”与‘’，英文上下文使用 "" 与 ''
  - 中英文混杂的内容主要看该段落中表意文字的语言，段落以中文表意文字为主时整段按中文上下文处理
  - 代码块、行内代码与链接语法内部不受此规则约束，按其自身语法书写
- 中文字符与 ASCII 字符之间包含一个半角空格，中文标点与 ASCII 字符之间不加空格
  - 行内代码整体视为一个 ASCII 单元，与两侧内容按上述规则处理，不受代码内部字符影响
- 段落中的内容按句号或分号单句换行，不按字符数硬折行
- 可以使用 Mermaid 图表达的图形不使用 ASCII 字符画

## 强调与符号

- 正文中的强调应当稀少，仅用于真正需要突出的内容，不机械加粗关键词
- 不使用表情符号装饰标题、列表项与正文
- 不在正文中使用 `→`、`←`、`⇒` 等箭头符号表示递进或转变关系，改用“到”、“至”、“向”、“转向”等文字表达

## 反引号

行内代码标记，即反引号，仅用于以下类型，其余情况一律不加：

- 代码片段与代码元素，例如 `print()`、`async def`
- 命令，例如 `git commit`、`uv sync`
- 文件路径，例如 `src/main.py`
- 文件名，例如 `README.md`
- 标识符，例如变量名 `user_id`、函数名 `getUserData`、类型名 `UserService`

以下情况不使用反引号：

- 普通术语与概念词，例如渐进式披露、面向对象、微服务
- 强调，使用粗体而非反引号
- 英文单词仅因为它是英文，例如 markdown 作为普通名词时
- URL 与电子邮件地址，使用链接语法而非反引号
- 表格中若某列所有单元格都属于上述应加反引号的类型，则该列整体省略反引号

## 链接与邮箱

- 引用外部网页时使用行内链接 `[链接文字](URL)`，链接文字应描述目标内容，避免“点击这里”等无信息表述
- 需要直接展示 URL 本身时使用尖括号自动链接 `<https://example.com>`，不写裸 URL
  - 裸 URL 在不同渲染器中行为不一致，尖括号是 CommonMark 标准保证的自动链接语法
- 邮箱地址使用尖括号自动链接 `<user@example.com>`，渲染为可点击的邮件链接
- 引用项目内的其他文件时，链接目标写相对当前文件所在目录的路径，例如 `docs/` 下的文档引用根目录说明时写 `[项目说明](../README.md)`
  - GitHub 等平台与编辑器都按当前文件位置解析相对链接，这样写在各处都能直接点击跳转
  - 不写以 `/` 开头的路径与本机绝对路径，它们在不同渲染器中指向不同位置

## 标题

- 标题使用名词短语，不写成对话式问句或祈使句，形式上接近论文小标题或工具书条目
- 标题层级逐级递进不跳级，单个文档只有一个一级标题
- 子标题最多使用 3 级，文档的一级标题不计入
- 标题中不使用括号，需要补充英文术语或说明时移至标题后的正文
- 标题默认不添加序号，仅在用户明确要求时使用
  - 使用序号时按 1、1.1、1.1.1 的格式逐级编号

## 列表

本节规则同时适用于有序列表与无序列表。

- 单个列表项应能在一句话内表达完整，超出时改用多级列表或回归段落
- 列表尾部不附加除问号外的任何标点符号
- 对于“要点：解释说明”的列表格式，不对“要点”部分加粗
- 连贯的论述不拆成“加粗小标题加冒号”式的列表，应写成段落

## 表格

- 单元格内容保持在短语级别，需要展开说明时在表格下方用段落补充
- 表格源码按列对齐竖线，中文字符按 2 字符宽度计算
- 若某列所有单元格内容都属于应加反引号的类型，则该列整体省略反引号，仅在列内混合代码与普通文字时保留
- 不使用合并单元格等 GFM 表格语法不支持的结构
