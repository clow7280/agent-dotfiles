# Git 提交规范

提交信息遵循基于 Conventional Commits v1.0.0 修改的以下规范，未明确的部分按原规范执行。
一个提交只做一件逻辑上的事，同一改动涉及的代码、测试与文档放在同一个提交中，不按文件类型拆分。

## 标题格式

- 标题格式为 `<type>(<scope>): <desc>`，项目未声明 scope 时省略括号部分，写作 `<type>: <desc>`
  - 例如 `NEW(label): 面名称支持固定标注在面外侧`、`CHG: 解锁服务的 PL1 功耗上限改为 70W`
- 标题全长不超过 72 个字符，中文字符按 2 个字符计算

### type

type 按改动对使用者或读者的意义选择，只允许以下 5 种。

| type | 含义                                                   |
| ---- | ------------------------------------------------------ |
| NEW  | 新增此前不存在的功能或内容                             |
| CHG  | 改变已有功能的行为或已有内容，包括删除                 |
| FIX  | 修正与预期不符的行为或内容                             |
| REF  | 不改变外部行为的结构调整，如重构、改名、移动、格式整理 |
| MNT  | 依赖、版本号、构建配置、忽略规则等维护                 |

- 在已有功能上增加此前没有的能力时用 `NEW`
- 原状态符合当时的预期、因需求变化而改动时用 `CHG`，原状态本身有误时用 `FIX`
- 无法确定类型时，跳出对话与用户讨论，不自行任意确定

### scope

- scope 表示受影响的模块或主题，例如 `fanctl`、`label`
- 可用的 scope 由项目在自身的 `AGENTS.md` 中声明，项目未声明时省略 scope，不自行发明
- 改动涉及多个已声明的 scope 时优先拆分提交
  - 确实不可拆分时省略 scope
- 无法确定 scope 归属时，跳出对话与用户讨论，不自行任意确定

### desc

- 使用中文简短描述改动内容，必要时才用英文补充
- 不写主语，默认以“本次提交”为主语
- 只写一件事，需要用顿号或逗号并列多项改动时，拆分提交或概括出共同目的
- 写改动后的结果而不是过程，例如不写“按评审修正”，而是写清修正了什么
- 不单独使用“更新”“调整”“优化”“修改”这类不说明方向的动词

## 正文

- 标题足以说明修改时不写正文
- 改动的原因与影响范围写在正文，不挤进标题
- 正文遵循 [Markdown 文档规范](markdown-writing.md) 的要求
- 永远不附加 `Co-authored-by` 等合作作者信息，也不附加 "Generated with" 等 AI 工具署名尾注
